一个常见疑问：OpenWrt 用的 Linux 内核是怎么升级的？直接替换内核？维护一个自己的 fork 分支？都不是。它采用的是"**上游 tarball + 本地补丁队列**"的模式，这套设计很值得借鉴。

## 仓库里根本没有内核源码

OpenWrt 的 git 仓库里没有 Linux 内核代码，只有"配方"：

```
target/linux/ramips/           ← MT7621 平台
├── Makefile                   ← KERNEL_PATCHVER=5.15 + tarball 的 sha256
├── config-5.15                ← 内核配置片段
├── patches-5.15/              ← 补丁队列（数百个 .patch，目录名绑定内核版本）
└── dts/                       ← 设备树（每台路由器一个文件）
```

编译时的实际动作：

1. 从 kernel.org 下载**官方原版 tarball**（`linux-5.15.211.tar.xz`，这就是 `make download` 阶段 dl/ 目录里的大文件）
2. 解压到 build_dir，按顺序打上全部补丁（quilt 管理）
3. 应用配置片段 + 各设备 DTS
4. 交叉编译

这些补丁就是 OpenWrt 与原版内核的全部差异：路由器特有的驱动（MT7621 的 NAND/PHY/时钟）、小 flash 优化等。**绝大部分改动会持续提交到上游 Linux**，进主线后 OpenWrt 就删掉本地补丁——补丁队列是"暂存待上游化"的性质。

## 升级是怎么做的

**小版本升级（5.15.209 → 5.15.211）**，最常见的形态是一次这样的提交：

```
kernel: bump 5.15 to 5.15.211
```

只改 Makefile 里的版本号和 hash，重新下载 tarball。LTS 的稳定补丁都是增量小改动，本地补丁队列几乎不用动。

**大版本升级（5.15 → 6.6，随发行版进行）**：

- 新建 `patches-6.6` 目录，把旧补丁逐个重新适配（rebase）：上游已吸收的删除、冲突的手工修改
- 各 target 重新生成 `config-6.6`
- 这是每个发行版开发周期的重头工作

**backport（向后移植）**：主线新内核修了重要 bug，维护者挑出单个 commit 做成补丁塞进当前版本，不等大版本升级。

## 为什么不 fork

对比"fork 整个内核仓库自己维护"的方案（很多厂商 SDK 就是这么干的），tarball+patch 的好处：

1. **紧跟上游零成本**：升级内核 = 换 tarball + 重放补丁，不用处理几万行的 merge 冲突
2. **差异透明可审计**：OpenWrt 对内核的全部改动就摆在 patches-5.15 目录里，一眼可见；git 只管 OpenWrt 自己的改动
3. **可复现**：同样 hash 的 tarball + 同样补丁 = 任何人编出一模一样的内核
4. **上游优先的良性循环**：补丁以进主线为目标，长期包袱越来越少（反例是 Padavan，内核停在 3.4 彻底放弃了这个循环）

## 几个特殊设计

- **每个 target 可用不同内核版本**：老平台可能停在 5.15，新平台用 6.6，同一发行版内不强制统一
- **设备差异走 DTS**：同一颗 MT7621 的几十款路由器共享一个内核，差异全在各自设备树里
- **kmod 与内核强绑定的根源**：内核无稳定 ABI，自编固件的内核 hash 决定了能装哪些 kmod——官方源的 kmod 装不上自编固件就是这个问题，解法是把 kmod 编进固件或搭自家的 kmods 源

## 一句话总结

**OpenWrt = 上游 LTS 原版内核 + 一层"驱动适配与裁剪"补丁 + 设备树体系**。仓库里是差异，不在仓库里的是原厂；升级靠换 tarball + 重放补丁，而不是维护 fork。这个"配方式"工程模式，是它能同时跟上上游节奏和支持几百种嵌入式设备的关键。
